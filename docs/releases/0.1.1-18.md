# Nimlet 0.1.1 (18): consolidation and connectivity

Audit date: 2026-09-28. This is a development/TestFlight release, not an App Store launch.

## Observed before this release

- Running Mac executable: `/Applications/Mice.app/Contents/MacOS/Mice`, version 0.1.0 (17).
- The host listened on TCP 61413. `mice.away.enabled` was false; no TCP 61423 away listener was present.
- Mac Tailscale was Running/online; its iOS peer was offline. The phone's actual installed app version could not be read: CoreDevice timed out. Build availability in App Store Connect does not establish what is installed on the phone.
- All committed feature branches were already ancestors of origin/main except a two-file UI cleanup. Its caption removal and dock behavior have been superseded by the newer composer/dock; the merge deliberately retains those replacements.
- The original working directory held a distinct, uncommitted commercial candidate 1.0 (15), including compiled LAN-only policy. It was not the running 0.1.0 (17) application.

## Why another Wi-Fi or cellular fails

Bonjour discovers a Mac on the local network; it does not supply an internet route. The current host had direct internet access disabled, and its configured VPN had no online phone peer. Previously `PublicAddress.interfaces()` also discarded all utun interfaces, so a paired phone never automatically learned its Mac's Tailscale address.

The existing direct path asks the router for PCP/NAT-PMP/UPnP forwarding and advertises global IPv6. These are candidate addresses, not proof of outside reachability. Carrier NAT, router policy and firewalls can prevent incoming traffic. The APNs worker only forwards encrypted notifications; it cannot relay input, video or audio. A STUN public address does not prove a TCP mapping works or rule out carrier NAT.

## Changes in this release

- Integrate the latest audio, pacing, notification and reconnect baseline, plus Nimlet branding, StoreKit Pro, packaging scripts and historical launch-preparation documents.
- Default development builds permit remote access. An explicitly compiled `MICE_LAN_ONLY` distribution remains possible. No app-review status or public website policy is changed by this release.
- Advertise Tailscale IPv4 and IPv6 addresses only when they belong to an active tunnel interface. Do not treat an ordinary carrier address as a VPN.
- Keep the wire format compatible: VPN candidates use the existing pairing-code TLS path inside the separately authenticated VPN. They do not require the public away listener, and the six-character pairing code is not used on the public away port.
- Prefer LAN candidates, then VPN candidates, then public candidates. Preserve saved candidates across reconnect and launch.
- Show VPN route/address and explain when direct access is off. Keep public forwarding opt-in. Show the saved explanation when a phone cannot discover the Mac.
- Preserve newer audio and push privacy disclosures and add StoreKit/VPN disclosures.

## Using a different network

1. Update both apps to build 18. Connect the phone to the Mac once so it receives the candidate addresses.
2. Connect Tailscale on both devices, using the same authorized tailnet. Keep the Mac awake and Nimlet running.
3. Change the phone to cellular or another Wi-Fi and reconnect. If needed, use the VPN address and actual listening port shown in the Mac menu under VPN. VPN access does not require enabling public port forwarding.
4. Settings → Network shows the selected route. Verify text delivery, window preview and audio on the physical phone.

Alternative: enable Reachable on cellular in the Mac menu while paired locally, then inspect the router status. A saved public address is not an external reachability test. A first-party automatic control relay is a separate future transport project; it is not included in build 18.

## Validation and delivery

Evidence is under `build/release-18/` in the main checkout. Verified locally: 489 Mac/shared unit tests, 16 existing iOS TLS/audio connection tests, one new VPN setup-persistence test, four notification-worker tests, both Release builds, signed iOS archive and CLI build. The first added-test build exposed an optional-array assertion error; it was fixed and the test passed. The Mac installer verified the signature and installed build 18; a live TLS probe received protocol 23 and confirmed Accessibility granted. The probe's CLI identity remains unapproved, so this is not an input-delivery test. StoreKit purchase, restore and eventual refund-revocation testing passed on iOS 27.1 after restarting a hung test session and correcting the test to wait for asynchronous revocation propagation. This does not establish real Sandbox/TestFlight purchase acceptance. Upload completed successfully at 17:40 China time; Apple reported the package is processing. Browser verification of completed TestFlight processing and tester availability was unavailable because App Store Connect was signed out. The uploaded production source is commit `03957a5`; subsequent release-record/test-only changes do not alter the app binary. Physical cellular control, phone installation, live StoreKit purchase, notification delivery and App Store review are separate acceptance steps.
